# HANDOFF — M24 deferred slate (round 43): post-rep coach note's IM tone-drill trio is anchored on the just-finished rep's scenario — the defensive symmetric pin to round 41 (SOLVED freshness on the chat-coach context surface) and round 42 (TRAJECTORY freshness on the chat-coach context surface). The post-rep note doesn't need a freshness gate because, by construction, the read IS the just-finished rep's scenario — the user just produced the rep that anchors the read. Round 43 lifts the inline IM tone-drill block out of `PracticeSessionFinalizer.recordPostRepCoachNote` and into a pure `MomentumComputer.imToneDrillNoteFields(forJustFinished:in:)` helper so the per-rep anchoring contract is testable in isolation, then locks the contract with a 14-test `PostRepCoachNoteJustFinishedRepAnchoringTests` suite. Pure refactor + tests, no behavior change, no schema bump, no view changes.

## Scope

Rounds 41 + 42 closed the freshness gaps on the chat-coach context's SOLVED and TRAJECTORY surfaces — the chat coach no longer narrates a months-old crossing or a months-old below-bar drill the user hasn't returned to. Future move #21 from round 42's HANDOFF named the symmetric question on the post-rep coach note surface: does the same cross-rep cold-open risk exist there? The user finishes an IM rep in scenario A; could the deterministic note's TRAJECTORY branch reach for scenario B's old (sub-bar, slipping) trajectory instead — the way the chat-coach context did before rounds 41/42?

Round 42 looked at the wiring and judged it implicitly fresh by structure: `PostRepCoachNoteInput.imToneDrillProgress` is the freshly-computed progress for the just-finished rep's scenario (`IMHistorySummary.toneDrillProgress(from: allSessions, scenario: details.setup.scenario)`), not a global "freshest trajectory anywhere" read. The note's TRAJECTORY branch only fires when `imToneDrillProgress` is non-nil, and uses `imToneDrillScenarioTitle` (also derived from the just-finished rep). So a cross-rep cold-open is structurally impossible — but the structural contract was inline in a private function in the finalizer, not testable in isolation.

Round 43 makes the contract testable in isolation. The lightest possible refactor: lift the inline block (`PracticeSupport.swift:7796-7844` before round 43, ~50 lines of `if session.mode == .imConversation { ... } else { ... }`) into a single pure static helper on `MomentumComputer` (the same enum that houses `MomentumComputer.compute` for filler/score momentum signals). The helper takes `(session, allSessions)` and returns an `IMToneDrillNoteFields` struct with the six optional fields the finalizer was already setting (`progress`, `scenarioTitle`, `toneTitle`, `resolved`, `resolvedScenarioTitle`, `resolvedToneTitle`). The finalizer now calls one line instead of inlining the 50; behavior is byte-identical.

The new test suite (`PostRepCoachNoteJustFinishedRepAnchoringTests`, 14 `@Test` methods) pins the structural anchoring contract on every branch — non-IM reps return empty, IM reps without `imConversationDetails` (legacy) return empty, titles are anchored on the just-finished rep's `details.setup`, thin per-scenario history returns nil progress with non-nil titles, the trio NEVER picks up another scenario's trajectory even when that scenario has a textbook 4-rep below-bar slip, the SOLVED resolved trio is nil for sub-bar just-finished reps even when another scenario had a prior crossing, the resolved trio fires on the crossing rep, and two end-to-end tests through `PostRepCoachNoteService.deterministicNote(input:)` prove the cross-rep cold-open is structurally impossible at the surface level (the note never names a scenario other than the just-finished rep's).

## What shipped

### Track 1 — `MomentumComputer.imToneDrillNoteFields(forJustFinished:in:)` static helper (`Noum/PostRepCoachNoteService.swift`)

- New `static func imToneDrillNoteFields(forJustFinished session: PracticeSession, in allSessions: [PracticeSession]) -> IMToneDrillNoteFields` — pure helper. Guards on `session.mode == .imConversation` + non-nil `imConversationDetails` (returns `.empty` on either failure), then threads `details.setup.scenario` through `IMHistorySummary.toneDrillProgress(from:scenario:)` (for the trajectory trio) and `IMHistorySummary.toneDrillCrossing(in:scenario:currentRepId:)` (for the resolved trio). The trio's titles come from `details.setup.scenario.title` + `details.setup.targetTone.title` — never from a global "most common scenario/tone" read across history.
- Placed at the end of the `MomentumComputer` enum so it sits as one symmetric per-rep helper alongside the existing momentum computations.
- Pinned by 11 helper-level tests in the new suite (see Track 3) covering empty cases, title anchoring, thin-history nil-progress, the cross-rep anchoring contract, and the SOLVED resolved trio's anchoring contract.

### Track 2 — `IMToneDrillNoteFields` struct (`Noum/PostRepCoachNoteService.swift`)

### Track 4 — `PostRepCoachNoteJustFinishedRepAnchoringTests` suite (`NoumTests/NoumTests.swift`)

Fourteen new `@Test` methods inside a new `struct PostRepCoachNoteJustFinishedRepAnchoringTests` suite, slotted immediately after the existing `PostRepCoachNoteToneTrajectoryTests` suite (`PostRepCoachNoteToneResolvedTests` follows). Four private fixture helpers (`imSession(id:scenario:targetTone:actualTone:daysOffset:)` with optional explicit id for the crossing tests, `nonIMSession(daysOffset:)` for the non-IM branch, `slippingScenarioSessions(scenario:targetTone:offBrandTone:earliestDayOffset:)` mirroring the round-42 helper exactly, and `crossingScenarioSessions(scenario:targetTone:offBrandTone:onBrandTone:crossingRepId:earliestDayOffset:)` for the SOLVED-crossing-rep tests).

- **Helper — empty cases (2 tests):**
  - `helperReturnsEmptyForNonIMReps` — non-IM rep (Timed) returns all-nil even when an IM scenario has a textbook slipping trajectory in the session set.
  - `helperReturnsEmptyForIMRepWithoutConversationDetails` — defensive: `mode == .imConversation` but `imConversationDetails == nil` (legacy persisted sessions) returns all-nil rather than crashing.
- **Helper — title anchoring (2 tests):**
  - `helperAnchorsScenarioTitleOnJustFinishedRep` — `scenarioTitle` comes from the just-finished rep's `details.setup.scenario.title`.
  - `helperAnchorsToneTitleOnJustFinishedRep` — `toneTitle` comes from the just-finished rep's `details.setup.targetTone.title`, even when prior reps in the same scenario targeted a different tone (the user re-targeted).
- **Helper — thin per-scenario history (1 test):**
  - `helperReturnsThinHistoryNilProgressWithNonNilTitles` — just-finished rep is the only rep in its scenario; progress is nil (below the 4-rep floor); titles remain set.
- **Helper — cross-rep anchoring (the core round-43 contract, 3 tests):**
  - `helperProgressIgnoresOtherScenariosWhenJustFinishedRepIsThin` — just-finished rep in scenario A (thin); scenario B has a 4-rep below-bar slip; helper returns scenario A's titles and nil progress — NEVER scenario B's slip.
  - `helperProgressReadsFromJustFinishedRepsScenarioOnlyWhenBothQualify` — both scenarios qualify for `toneDrillProgress`; scenario A is recovering, scenario B is slipping. Just-finished rep is in scenario A → progress direction is `.recovering`, not `.slipping`.
  - `helperProgressIsForJustFinishedScenarioEvenWhenOtherScenarioWouldFireMoreLoudly` — just-finished rep in scenario A (thin, on-brand); scenario B has the loudest open slip in the set. Helper still surfaces only scenario A's titles with nil progress.
- **Helper — SOLVED resolved trio anchoring (3 tests):**
  - `helperReturnsNilResolvedWhenJustFinishedRepIsNotTheCrossingRep` — just-finished rep is a sub-bar drill rep in scenario A; scenario B had a prior crossing. Resolved trio is nil for the just-finished rep.
  - `helperPopulatesResolvedTrioOnCrossingRep` — just-finished rep IS the crossing rep (constructed via `crossingScenarioSessions`); resolved trio fires; `resolved.scenario` equals just-finished rep's scenario; `resolved.targetTone` equals the dominant evaluated tone for the scenario.
  - `helperResolvedTrioAnchorsOnJustFinishedRepScenarioTitle` — `resolvedScenarioTitle == scenarioTitle` (both routed through `IMConversationScenario.title`).
- **Cross-surface contract via `deterministicNote` (3 tests):**
  - `deterministicNoteNeverNamesAnotherScenarioWhenJustFinishedRepIsThin` — end-to-end pin on the cross-rep cold-open path. Just-finished rep in scenario A (thin); scenario B has a fresh slip. The deterministic note NEVER mentions scenario B's title under any voice.
  - `deterministicNoteSpeaksToJustFinishedScenarioOnRecoveringTrajectory` — happy path. Just-finished rep in scenario A (recovering but below the 60% hold-bar, so the SOLVED branch doesn't fire and the trajectory branch does). The note headlines scenario A; scenario B (slipping in the same session set) is never mentioned.
  - `deterministicNoteHeadlinesResolvedWinOnlyForJustFinishedRepsScenario` — SOLVED-branch cross-surface pin. Just-finished rep is sub-bar in scenario A; scenario B had a prior crossing. The note's SOLVED branch stays quiet; scenario B's old crossing never headlines the note for a scenario A rep.
